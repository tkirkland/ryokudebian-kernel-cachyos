# ryokudebian-kernel-cachyos

The CachyOS kernel (BORE scheduler, CachyOS config) with OpenZFS compiled in
(`CONFIG_ZFS=y`: no `zfs.ko`, no dkms), packaged as Debian `.deb`s, built
weekly in CI. It is the install-time alternative to the default kernels from
[tkirkland/ryokudebian-kernel](https://github.com/tkirkland/ryokudebian-kernel)
for Ryoku Debian, the Ryoku port to Debian trixie (decision D-06), and is built the same way.

## What a release holds

A release named `<cachyos tag>-<zfs tag>`, for example `7.2.11-1-zfs-2.4.4`:

- `linux-image-<kver>-cachyos_<cachyos ver>-zfs<zfs ver>_amd64.deb`
- `linux-headers-<kver>-cachyos_..._amd64.deb`
- `zfs-userland.tar.gz`: the ZFS tools from the same OpenZFS tree, all paths
  under `/usr`, systemd units included. Unpack at `/`.

The image deb is about 320 MB (344 MB unpacked): CachyOS's config builds a
much wider module set than Debian's. Modules are stripped already.

The kernel release string is `<kver>-cachyos` (for example `7.2.11-cachyos`),
so the packages never collide with ryokudebian-kernel's `<kver>-ryokudebian` ones
and both can be installed side by side. The Debian revision carries the
OpenZFS version, so a rebuild against a newer OpenZFS upgrades in place.

## How it works

- `plan.sh` (weekly, and on manual dispatch) takes the latest OpenZFS release,
  reads its `META` `Linux-Maximum`, and pins the current
  [CachyOS/linux-cachyos](https://github.com/CachyOS/linux-cachyos) and
  kernel-patches commits. It
  builds `linux-cachyos-bore` when its major is supported, else falls back to
  `linux-cachyos-lts` (with BORE too). Already-published releases are skipped.
- After a release has all its assets uploaded, `prune.sh` keeps it plus the
  previous release (by publish time, so an lts fallback still counts as
  current) and deletes the rest with their git tags. A failed build never
  prunes. `KEEP=<n>` changes the count.
- `build.sh` runs inside `docker run debian:trixie`:
  1. the pre-patched source tarball from
     [CachyOS/linux](https://github.com/CachyOS/linux/releases) releases
     (`cachyos-<ver>-<rel>`), the `config` from the pinned linux-cachyos
     commit, and `sched/0001-bore-cachy.patch` from the pinned
     [CachyOS/kernel-patches](https://github.com/CachyOS/kernel-patches) commit;
  2. the defaults the linux-cachyos-bore PKGBUILD applies on top of `config`:
     `CACHY`, `SCHED_BORE`, 1000 Hz, full tickless, full preempt, `-O3`,
     THP always;
  3. OpenZFS grafted in with `copy-builtin`, `CONFIG_ZFS=y`, then
     `make bindeb-pkg`;
  4. the ZFS userland built from the same tree.

## Decisions

**Version: CachyOS 7.2.11-1** (first release), the newest `linux-cachyos-bore`.
OpenZFS 2.4.4 declares `Linux-Maximum: 7.2`. CachyOS's 7.3 is still at -rc.

**Scheduler: BORE, from the `linux-cachyos-bore` variant.** CachyOS's flagship
`linux-cachyos` package now defaults to plain EEVDF: its source tarball does not
contain BORE, and its PKGBUILD only adds the BORE patch for the `bore`,
`rt-bore` and `hardened` variants. The `linux-cachyos-bore` config is
byte-identical to `linux-cachyos`'s; only the scheduler patch and the
toolchain differ.

**Toolchain: gcc (trixie's 14.2), not clang + ThinLTO.** This matches what
CachyOS itself ships for this variant: `linux-cachyos-bore` builds with
`_use_llvm_lto=none`, only the EEVDF flagship uses clang ThinLTO. Trixie's
clang 19 would be new enough (the 7.2 tree needs LLVM 17 or later), but gcc
also avoids two problems a clang build brings:

- out-of-tree modules (NVIDIA DKMS) would have to be built with `LLVM=1` and
  clang installed on the target, which Debian's DKMS packages do not do;
- ThinLTO over a builtin ZFS is untested anywhere upstream (CachyOS builds ZFS
  as a module).

The cost is the few percent ThinLTO buys. Building with clang later means
`LLVM=1` on every `make`, `KERNEL_LLVM=1` on the ZFS `configure`, CachyOS's
`misc/dkms-clang.patch`, and `-e LTO_CLANG_THIN`.

Rust stays on: trixie's rustc 1.85 and bindgen 0.71.1 are exactly the 7.2
tree's minimums. CachyOS's config was generated by gcc 16; against gcc 14 the
only options lost are compiler-capability flags (`CC_HAS_*`, LTO/AutoFDO
availability), which the build log lists under "CachyOS options dropped".

**CPU baseline: generic x86-64 (v1)**, as CachyOS's `config` has it. The
PKGBUILD's empty `_processor_opt` would switch to `-march=native`, which is
wrong on a CI runner. CachyOS's own v3/v4 repos build higher baselines; this
repo does not.

**Debug info: DWARF5 + BTF, as CachyOS ships.** BTF is required by
`SCHED_CLASS_EXT` (sched_ext, the scx schedulers). The `-dbg` package it would
produce is skipped with the `pkg.linux-upstream.nokerneldbg` build profile.

## Known gaps

- **No lockdown under Secure Boot.** Debian's kernels carry a patch that turns
  on lockdown when booted with Secure Boot; this tree does not. The kernel is
  meant to boot inside a UKI signed per machine with its own MOK key, so the
  boot chain is verified, but the running kernel does not lock itself down.
- **Modules are signed with a throwaway key.** `MODULE_SIG_ALL` signs the
  in-tree modules with a key generated during the build and thrown away. CI
  holds no signing keys and must never hold them. DKMS modules need signing on
  the machine.
- **No source signature check.** The CachyOS tarball is fetched over HTTPS from
  its GitHub release; its `.asc` is not verified.
- **x86-64 v1 only**, no v3/v4 or znver4 builds.
- AutoFDO / Propeller profiles, which CachyOS uses for its clang kernels, do not
  apply to a gcc build.
- Not boot-tested yet (see below).
